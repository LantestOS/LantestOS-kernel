# M4-47c — 僵尸滞留就绪队列：defer_next 拆分与 kfree 取证

> 状态：**已提交**；fresh-disk `make test` **7/10，PANIC 0**（修复前同口径 6/10 且含 `kfree: double free`）
> 残留：3/10 静默冻结（tick 200–310，无 PANIC），G2 未达标，v0.1.0 仍被阻塞
> 日期：2026-11-01

## 1. 归因更正（重要）

M4-47b 文档把"AP 拉起竞态（`-d int` 下 8/8 挂）"留给 M4-47c。本轮实测证明：
**该竞态就是 ICR pending 丢弃（M4-47b 已修复）**——INIT/SIPI 同样经 ICR 发送，
上一包未排空时被硬件静默丢弃，症状正是"AP 不上线"。证据：

- 重试补丁（INIT/SIPI 3 轮重发）实测 `re-INIT=0`：AP 全部首轮上线，重发代码从未触发；
- 干净 M4-47b 主线上 `-d int` 连跑 6/6 `online=3`（此前 8/8 挂的形态消失）；
- 重试补丁属死代码，已回滚未提交。

## 2. 真凶：kfree: double free（尸检过程）

run4 panic 后取证（`docs/evidence-kfree-double-free.log`）+ 代码解剖定位三处互相咬合的缺陷：

1. **`rq_next` 被两条链表复用**：`task_reap` 把任务挂进 deferred 队列用的是
   `t->rq_next`，而该任务此时**仍链在 per-CPU 就绪队列上**（从未摘除）。
   deferred 链与 run queue 链互相踩踏同一指针字段 → 链表撕裂；
2. **僵尸可在就绪队列里存活并被再次调度**：AP 时间片到期时把 RUNNING 任务
   以 READY 重新入队；若任务随后 exit 成 ZOMBIE， reap 时它还挂在队列里，
   `task_finish_reap` 释放 `t` 后，AP 的队列尾部仍指向已释放内存；
3. fork_regs 生命周期正确（消费即置 NULL），排除。

## 3. 修复

- `include/task.h`：新增 `defer_next`，deferred 链**不再复用** `rq_next`；
- `arch/x86_64/percpu.c`：新增 `percpu_remove_task()`（在 rq_lock 内摘除任意位置的队列节点）；
  `task_reap` 在 unlink 全局任务表之前**先**从所属 CPU 就绪队列摘除；
- `sched/scheduler.c`：`ap_schedule()` 出队时跳过 ZOMBIE/DEAD；
  deferred 队列 drain/回填改用 `defer_next`；
- `mm/kmalloc.c`：`kfree` 在 double free / bad magic 时打印
  `size/ptr/caller=__builtin_return_address(0)`（凶手会自己报名字）。
